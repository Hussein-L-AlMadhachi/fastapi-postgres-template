# The `DB` wrapper

`db.py` gives you one small async wrapper around an `asyncpg` connection pool for Postgres.

What you get:

- one pool for the whole app, one borrowed connection per request
- query helpers that hand back plain `dict` rows instead of `asyncpg.Record`
- `insert`/`insertMany` for the insert boilerplate, with validated table and column names
- a transaction block for grouping writes

What you do not get: an ORM, models, lazy loading, or helpers for `UPDATE`/`DELETE`/count. Those are raw SQL, by design. Schema changes are not automated: the files in `migrations/` are plain SQL you run yourself.

## 1. Opening a connection

### Where the credentials come from

`lib/config.py` resolves the DSN, in this order:

1. the `dsn` argument you pass to `connect()` or `db_context()`
2. `DATABASE_URL`
3. a URL built from the libpq variables: `PGHOST` (default `127.0.0.1`), `PGPORT` (`5432`), `PGUSER` (`postgres`), `PGPASSWORD` (empty), `PGDATABASE` (`app`)

A `.env` file at the project root is loaded on import, so running the backend locally needs no exports. Copy `.env.example` to `.env` and edit it. Real environment variables are never overwritten by the file, so production and CI keep using what you inject there.

Because the fallback reads the `PG*` names, `psql` connects to the same database with no extra flags. With `DATABASE_URL` set, the URL form works too: `psql "$DATABASE_URL" -f migrations/0001_init_db.up.sql`.

Any `postgres://` URL is rewritten to `postgresql://`, which is the scheme asyncpg expects.

### `connect(dsn=None, *, min_size=1, max_size=10)`

Opens the shared pool. It is idempotent, a second call returns the pool that is already open.

```python
import asyncio
import db

async def main():
    await db.connect()
    try:
        async with db.db_context() as conn:
            ...
    finally:
        await db.disconnect()

asyncio.run(main())
```

In the app you never call it yourself. `server.py` opens the pool in the FastAPI lifespan and closes it on shutdown, so every request sees a warm pool.

### `disconnect()`

Closes the pool and every idle connection. Requests already holding a connection finish first.

### `db_context(dsn=None)`

An async context manager that borrows one pooled connection and returns it on exit.

```python
import asyncio
import db

async def main():
    async with db.db_context() as conn:
        database = db.DB(conn)
        print(await database.scalar("SELECT count(*) FROM items"))

asyncio.run(main())
```

Outside the app there is no lifespan, so `db_context` opens a temporary pool for the block and closes it again. That means a script gets one pool for the whole `async with`, not one per query: put your work inside a single block.

Pass a DSN to point a script at a different database:

```python
async with db.db_context("postgresql://localhost/scratch") as conn:
    ...
```

### `get_db()`

The FastAPI dependency. It borrows a pooled connection for the duration of one request and returns it to the pool afterwards.

```python
from fastapi import Depends
import asyncpg

from db import get_db

async def handler(conn: asyncpg.Connection = Depends(get_db)):
    ...
```

From there you either use the connection directly or wrap it: `DB(conn)`.

Do not open a new `db_context()` per query inside a request. One connection per request is the rule, it keeps the pool small and the transaction boundaries obvious.

### Connections are returned, not closed

`get_db` and `db_context` take a connection out of the pool and give it back. Never call `conn.close()` on a borrowed connection: the pool expects to reuse it, and a closed connection is only replaced on the next acquire.

## 2. Quick start

A complete, runnable script:

```python
import asyncio
import db

async def main():
    async with db.db_context() as conn:
        database = db.DB(conn)

        await database.executescript("""
            CREATE TABLE IF NOT EXISTS melons (
                id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                name TEXT NOT NULL,
                weight DOUBLE PRECISION
            );
        """)

        melon = await database.insert("melons", {"name": "sugar baby", "weight": 4.2})
        print(melon)                                      # {'id': 1, 'name': 'sugar baby', 'weight': 4.2}

        print(await database.fetchOne("SELECT * FROM melons WHERE id = $1", melon["id"]))
        print(await database.scalar("SELECT weight FROM melons WHERE id = $1", melon["id"]))

        status = await database.execute(
            "UPDATE melons SET weight = $1 WHERE id = $2", 5.0, melon["id"]
        )
        print(status)                                     # 'UPDATE 1'

        removed = await database.execute("DELETE FROM melons WHERE id = $1", melon["id"])
        print(removed)                                    # 'DELETE 1'

        print(await database.scalar("SELECT count(*) FROM melons"))  # 0

asyncio.run(main())
```

Every method on `DB` is `async`, so it must be `await`ed. Forgetting the `await` does not fail at the call site: the coroutine gets passed along and blows up later during response serialisation with `TypeError: 'coroutine' object is not iterable`. If you see that, look for a missing `await`.

Query parameters are positional and bound as Postgres placeholders, numbered from `$1`:

```python
await database.fetchAll(
    "SELECT * FROM items WHERE price > $1 AND name LIKE $2",
    10,
    "water%",
)
```

## 3. Raw statements

Use these when the helpers do not fit, for example for CTEs, window functions, `INSERT ... ON CONFLICT` or multi-statement scripts.

### `execute(sql, *params)` -> status tag

```python
status = await database.execute(
    "INSERT INTO items (name, price) VALUES ($1, $2) "
    "ON CONFLICT (name) DO UPDATE SET price = excluded.price",
    "melon",
    3.5,
)
```

`execute` returns the Postgres command tag as a string: `'INSERT 0 1'`, `'UPDATE 3'`, `'DELETE 2'`, `'CREATE TABLE'`. When you need the affected count:

```python
affected = int(status.split()[-1])
```

Statements commit on their own, unless you are inside `database.transaction()` (see section 6). There is no cursor object to close, asyncpg handles the protocol.

### `executemany(sql, rows)` -> number of rows

`rows` is any iterable of sequences. The return value is how many parameter rows you handed in, because Postgres does not report per-row counts for a batched call.

```python
inserted = await database.executemany(
    "INSERT INTO items (name, price) VALUES ($1, $2)",
    [("melon", 3.5), ("pumpkin", 12.0)],
)
print(inserted)   # 2
```

The statement must not return rows: no `RETURNING` here, use `insert` for that.

### `executescript(sql)`

Runs several statements separated by semicolons. No parameters, no return value. Handy for `CREATE TABLE` blocks in tests or for applying a migration file:

```python
await database.executescript(open("migrations/0001_init_db.up.sql").read())
```

`executescript` runs through the simple query protocol, which wraps the whole script in one implicit transaction. A failure rolls the entire script back.

## 4. Reading rows

Helpers here never mutate. Each one asks asyncpg for the rows and converts them to dicts.

### `fetchOne(sql, *params)` -> `dict | None`

```python
item = await database.fetchOne("SELECT * FROM items WHERE id = $1", 1)

if item is None:
    ...  # nothing matched
else:
    print(item["name"])
```

Returns `None` when nothing matched. This is the helper to use for lookups; it does not raise on empty results.

### `fetchAll(sql, *params)` -> `list[dict]`

```python
items = await database.fetchAll("SELECT * FROM items ORDER BY id")
for item in items:
    print(item["id"], item["name"])
```

Empty result gives `[]`. This materialises the whole result set, so do not point it at a million rows.

### `fetchMany(sql, size, *params)` -> `list[dict]`

The size goes before the query parameters, not after:

```python
page = await database.fetchMany("SELECT * FROM items ORDER BY id", 20)
```

It reads through a server-side cursor inside a short transaction, so the database only sends `size` rows over the wire. Use it for previews and "first N" queries. For real pagination, use `LIMIT`/`OFFSET` (or keyset pagination) in the SQL itself.

### `iterate(sql, *params, size=256)` -> async generator

Streams rows in chunks so memory stays flat regardless of result size.

```python
async for item in database.iterate("SELECT * FROM items ORDER BY id", size=500):
    await publish(item)
```

The cursor lives inside a transaction, which stays open for as long as you stream. That gives you a consistent snapshot, and it also means a slow consumer holds a snapshot back. Keep those loops short. If you leave the loop early, close it explicitly with `await stream.aclose()` where `stream` is the generator:

```python
stream = database.iterate("SELECT * FROM items ORDER BY id")
try:
    async for item in stream:
        if item["id"] > 100:
            break
        await publish(item)
finally:
    await stream.aclose()
```

### `scalar(sql, *params)` -> `Any`

First column of the first row, `None` if there are no rows. Backed by `fetchval`.

```python
total = await database.scalar("SELECT count(*) FROM items")
newest = await database.scalar("SELECT max(created_at) FROM items")
```

### `pluck(sql, *params)` -> `list[Any]`

First column of every row. Nice for id lists.

```python
ids = await database.pluck("SELECT id FROM items WHERE price > $1", 10)
```

### `exists(sql, *params)` -> `bool`

True when the query returns at least one row.

```python
taken = await database.exists("SELECT 1 FROM items WHERE name = $1", "melon")
```

Write the query as a plain `SELECT ...`; `exists` does not wrap it, it only checks for a value. With an aggregate like `count(*)` the answer is always `True`, because aggregates always return a row.

## 5. Writing rows

Two helpers exist for inserts, because building an `INSERT` from a dict is pure boilerplate. Everything else (`UPDATE`, `DELETE`, `upsert`, `RETURNING`) is raw SQL through `execute`. This wrapper is not an ORM.

### `insert(table, values)` -> the new row

```python
item = await database.insert("items", {"name": "melon", "price": 3.5, "tax": None})
print(item["id"])   # 1
```

It runs `INSERT ... RETURNING *` and gives you the whole row back, so you get the generated id, defaults and anything a trigger touched without a second query.

### `insertMany(table, rows)` -> number of rows

```python
count = await database.insertMany("items", [
    {"name": "melon", "price": 3.5, "tax": None},
    {"name": "pumpkin", "price": 12.0, "tax": 1.2},
])
```

Every dict must have the same columns. The column list comes from the first row; a later row missing a key raises `ValueError("row is missing column ...")`. Extra keys in later rows are ignored.

An empty list returns `0` and touches nothing.

All rows go through one `executemany` call, which asyncpg sends as one batched statement. Wrap it in `transaction()` if it must be committed together with other writes.

### Changing rows

```python
status = await database.execute("UPDATE items SET price = $1 WHERE id = $2", 4.0, 1)
print(status)   # 'UPDATE 1'
```

The number is how many rows matched the `WHERE`, not "values that actually differed".

### Deleting rows

```python
status = await database.execute("DELETE FROM items WHERE id = $1", 3)
print(status)   # 'DELETE 1'
```

There is no `delete(table, where)` helper on purpose: writing the `WHERE` yourself means the destructive statement is visible in the code. A `DELETE` with no `WHERE` is one grep away from being obvious.

### Upserts, RETURNING and friends

```python
status = await database.execute(
    "INSERT INTO items (id, name, price) VALUES ($1, $2, $3) "
    "ON CONFLICT (id) DO UPDATE SET price = excluded.price",
    1,
    "melon",
    4.0,
)

created = await database.fetchOne(
    "INSERT INTO items (name, price) VALUES ($1, $2) RETURNING *", "melon", 4.0
)

total = await database.scalar("SELECT count(*) FROM items WHERE tax IS NULL")
```

Anything Postgres parses works: `ON CONFLICT DO NOTHING`, `ON CONFLICT ... DO UPDATE`, CTEs in front of `UPDATE`, `DELETE ... RETURNING`, `ALTER TABLE`. For nullable integer columns remember that Pydantic gives you `None`, not `0`.

## 6. Transactions

By default every statement commits as soon as it returns. To group several statements, use the transaction block:

```python
async with database.transaction() as tx:
    order = await tx.insert("orders", {"customer": "hussein"})
    await tx.insert("order_lines", {"order_id": order["id"], "sku": "melon"})
    await tx.execute("UPDATE stock SET count = count - 1 WHERE sku = $1", "melon")
```

- clean exit: one `COMMIT`
- any exception: `ROLLBACK`, and the exception keeps propagating
- inside the block, every helper uses the same connection and waits for the block

Catch your own errors outside the block if you want to keep going after a failure:

```python
try:
    async with database.transaction() as tx:
        await tx.insert("items", {"name": "melon", "price": 1.0})
        raise RuntimeError("something went wrong")
except RuntimeError:
    pass

# nothing was written
```

Nesting is allowed. asyncpg turns the inner block into a `SAVEPOINT`, so an inner failure can be rolled back without losing the outer work.

Check state with the property:

```python
database.in_transaction   # bool, straight from the asyncpg connection
```

A transaction block that raises inside an HTTP handler still leaves the connection usable, because the rollback happens before `get_db` returns it to the pool.

## 7. Value adaptation

asyncpg maps most Python types to Postgres types directly. The wrapper only touches containers:

| Python value | Bound as |
| --- | --- |
| `bool` | `boolean` |
| `int` | `bigint` / `integer`, depending on the column |
| `float` | `double precision` |
| `Decimal` | `numeric` |
| `datetime` / `date` | `timestamptz` / `date` |
| `dict`, `list`, `tuple` | JSON text (`json.dumps`), for `json`/`jsonb` columns |
| `None` | `NULL` |
| anything else | unchanged, asyncpg decides |

```python
await database.insert("events", {
    "name": "planting",
    "payload": {"rows": 3, "melons": ["a", "b"]},   # stored as json text
    "created_at": datetime(2026, 11, 4, 12, 30),    # stored as timestamptz
})

payload = await database.scalar("SELECT payload FROM events WHERE name = $1", "planting")
json.loads(payload)   # {'rows': 3, 'melons': ['a', 'b']}
```

Adaptation is one way. Reads hand back whatever type asyncpg decoded: `jsonb` comes back as a string unless you register a codec, `timestamptz` comes back as an aware `datetime`. Parse JSON yourself with `json.loads`.

Because dicts are silently JSON encoded, a mistake like passing a whole object where a scalar was meant will not raise, it will store JSON. Check column types when a query returns something surprising.

Two things asyncpg is strict about:

- a `str` is not accepted for an `integer`/`boolean` column, unlike sqlite. Send real `int`/`bool` values.
- a `float` is not accepted for `numeric`. Use `Decimal` when the column is `numeric`.

## 8. Schema introspection

```python
await database.tables()
# ['items', 'orders']

await database.columns("items")
# [{'column_name': 'id', 'data_type': 'bigint', 'is_nullable': 'NO',
#   'column_default': "nextval('items_id_seq'::regclass)"}, ...]
```

`tables()` lists the base tables in the current schema. `columns()` returns one dict per column, straight from `information_schema.columns`, ordered by position. Both read the schema that `search_path` resolves to, `public` by default.

## 9. Safety rules

One thing the wrapper enforces, one it cannot.

**Identifiers are validated.** Table and column names in `insert`, `insertMany` and `columns` must match `[A-Za-z_][A-Za-z0-9_]*`. Anything else raises before a statement is built:

```python
await database.columns("items; DROP TABLE items")
# ValueError: invalid sql identifier: 'items; DROP TABLE items'
```

Identifiers cannot be placeholders in SQL, because they are not values, so the wrapper checks their shape and quotes them with double quotes.

**Values are always placeholders.** Never format user input into the SQL string yourself:

```python
# don't
await database.fetchAll(f"SELECT * FROM items WHERE name = '{name}'")

# do
await database.fetchAll("SELECT * FROM items WHERE name = $1", name)
```

That is the part the wrapper cannot save you from: any `execute`/`fetchAll`/`scalar` string you build by hand is your responsibility.

## 10. Patterns used in this project

### A service that owns the queries

`model/items/service.py` is the intended shape. The service takes the request connection and is the only thing that knows SQL:

```python
from db import DB
from model.items.dto import Item
import asyncpg


class ItemsService:
    db: DB

    def __init__(self, conn: asyncpg.Connection):
        self.db = DB(conn)

    async def create(self, item: Item) -> int:
        row = await self.db.insert("items", item.model_dump())
        return row["id"]

    async def listAll(self) -> list[dict]:
        return await self.db.fetchAll("SELECT * FROM items ORDER BY id")

    async def fetch(self, item_id: int) -> dict | None:
        return await self.db.fetchOne("SELECT * FROM items WHERE id = $1", item_id)
```

The handler stays thin:

```python
@router.get("/")
async def root(conn: asyncpg.Connection = Depends(get_db)):
    items = await ItemsService(conn).listAll()
    return StandardResponse("ok", data=items).success()
```

### Streaming a large export

```python
@router.get("/export")
async def export(conn: asyncpg.Connection = Depends(get_db)):
    database = DB(conn)

    async def rows():
        async for item in database.iterate("SELECT * FROM items ORDER BY id"):
            yield json.dumps(item) + "\n"

    return StreamingResponse(rows(), media_type="application/x-ndjson")
```

The generator pulls from the cursor chunk by chunk, so the row set never sits in memory. The connection stays borrowed for the whole response, which is why the pool default is ten connections, not two.

### Bulk import in one transaction

```python
async def import_items(conn, rows: list[dict]) -> int:
    database = DB(conn)

    async with database.transaction():
        await database.execute("DELETE FROM items")
        inserted = await database.insertMany("items", rows)

    return inserted
```

## 11. Gotchas

**Missing `await`.** The most common mistake by far. An async helper returning a coroutine gives you `TypeError: 'coroutine' object is not iterable` at response serialisation, with a traceback pointing at FastAPI's encoder instead of your handler.

**Placeholders are `$1`, not `?`.** asyncpg speaks the Postgres protocol. A `?` in your SQL is either the JSONB key-exists operator or a syntax error, never a parameter.

**No `rowcount` and no `lastrowid`.** `execute` gives you the status tag, `insert` gives you the row. Reach for `insert(...)` or `RETURNING` instead of asking a cursor for the id.

**Column names are whatever Postgres returns.** `fetchOne("SELECT * FROM items")` returns keys exactly as the columns are declared or aliased. Use `SELECT price AS total_price` if you want a different key.

**`fetchMany` argument order.** `fetchMany(sql, size, *params)`. Written the other way round asyncpg complains about too many parameters for the query.

**Aggregates and `exists`.** `count(*)` always returns one row, so `exists("SELECT count(*) ...")` is always `True`. Select `1` instead.

**No `update`, `delete` or `count` helpers.** Deliberate. `UPDATE`, `DELETE` and counting are raw SQL through `execute` or `scalar`, so the `WHERE` clause is written out in the open instead of hidden behind a dict.

**Every helper commits.** Two `insert` calls without a transaction are two transactions. If the second fails the first stays. Use `transaction()` when the pair must be all or nothing.

**A pooled connection is shared, not owned.** Do not keep a reference to `conn` past the request, do not close it, and do not run `SET` statements on it expecting them to stick. The next request may get a different connection.

**`SET search_path` on one connection does not apply to the others.** Use `$user`/`public`, or set it in the pool's `server_settings` when you open it.

**Migrations are manual.** There is no runner. Apply a migration yourself and keep it small, so a failed statement is easy to reason about:

```bash
psql "$DATABASE_URL" -f migrations/0001_init_db.up.sql
```

`compose.yml` mounts `migrations/` read-only into the `db` service, so the same file is one command away:

```bash
docker compose up -d db
docker compose exec db psql -U postgres -d app -f /migrations/0001_init_db.up.sql
docker compose up -d backend
```

## 12. API reference

| Method | Returns | Notes |
| --- | --- | --- |
| `connect(dsn=None, min_size=1, max_size=10)` | pool | Opens the shared pool, idempotent |
| `disconnect()` | `None` | Closes the pool |
| `pool()` | pool | Raises if the pool is not open |
| `db_context(dsn=None)` | async context manager of connection | Borrows a pooled connection |
| `get_db()` | async generator of connection | FastAPI dependency |
| `DB(connection)` | `DB` | Wraps a borrowed `asyncpg.Connection` |
| `execute(sql, *params)` | `str` | Postgres status tag, e.g. `'UPDATE 3'` |
| `executemany(sql, rows)` | `int` | Number of parameter rows sent |
| `executescript(sql)` | `None` | Multiple statements, no parameters |
| `fetchOne(sql, *params)` | `dict \| None` | `None` when nothing matches |
| `fetchAll(sql, *params)` | `list[dict]` | Materialises the full result |
| `fetchMany(sql, size, *params)` | `list[dict]` | Size comes before parameters |
| `iterate(sql, *params, size=256)` | async generator of `dict` | Streams in chunks |
| `scalar(sql, *params)` | `Any` | First column of first row |
| `pluck(sql, *params)` | `list[Any]` | First column of every row |
| `exists(sql, *params)` | `bool` | True when at least one row comes back |
| `insert(table, values)` | `dict` | `INSERT ... RETURNING *` |
| `insertMany(table, rows)` | `int` | Number of rows inserted |
| `tables()` | `list[str]` | Base tables in the current schema |
| `columns(table)` | `list[dict]` | Rows from `information_schema.columns` |
| `transaction()` | async context manager | Commit on success, rollback on error |
| `in_transaction` | `bool` | Current connection state |

Not in the wrapper, on purpose: `update`, `delete`, `count`, `upsert`, joins, relations, lazy loading. Use `execute`, `fetchOne`, `fetchAll` or `scalar` with your own SQL.
